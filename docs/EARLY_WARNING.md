# Early-warning dissemination

WeatherGPT alerts come from the deterministic alert engine (`backend/alerts/engine.py`) running on Open-Meteo forecasts. **They are generated by WeatherGPT and are not official IMD warnings.** Every channel below says so:
- the alert cards, the banner, the advisory panel and the high-severity HUD
- the `note` on `/api/alerts`
- the push text, WhatsApp shares and the CAP `<note>` / `senderName` / `description`

## Channels

| Channel | Where | Status |
|---------|-------|--------|
| Web Push when severity **becomes high** | `backend/dissemination/job.py`, `backend/dissemination/push.py`, `public/sw.js` | Works once VAPID keys are set (sent with `pywebpush`, pinned in `backend/requirements.txt`) |
| WhatsApp share | Alert cards on `/alerts`, chat answers | Works (a `wa.me` link, no API key) |
| CAP 1.2 XML | `GET /api/alerts/cap?latitude=&longitude=&name=` | Works |
| Test push for demos | **Send test alert** on `/alerts` → `POST /api/push/test` | Works for signed-in users with a subscription |

### Test push for demos

On a calm day the job never sends anything, so `/alerts` has a **Send test alert** button for signed-in users who have at least one subscription. It calls `POST /api/push/test` with the user's Supabase access token (`Authorization: Bearer …`).

- **Auth:** the backend verifies the token with Supabase Auth (`GET /auth/v1/user`, which checks the signature) and takes the user id from that response.
- **Own subscriptions only:** rows are read with the user's own JWT and the anon key (RLS applies), filtered by `user_id=eq.<id>`, and any row for another user is dropped. The service-role key is not used.
- **Text:** title "WeatherGPT test alert", body "TEST: WeatherGPT demo alert, not an official IMD warning".
- **Rate limit:** one test per user per minute (HTTP 429 with `Retry-After`, in whole seconds, never more than 60). An attempt with no subscriptions does not use up the minute.

#### The rate limit is per backend process

The limiter (`dissemination/demo_push.py`, `RateLimiter`) is a dictionary in the backend's memory. That has three consequences:

| Deployment | What happens |
|------------|--------------|
| One uvicorn process (`uvicorn main:app`, the default and what `docs/DEPLOYMENT.md` uses) | Exactly one test per user per minute. |
| Several workers (`--workers 4`) or several instances behind a load balancer | Each process has its own memory, so a user can get up to one test per minute **per process**. |
| A restart or redeploy | The limit resets; a user can send a test straight away. |

This is acceptable for a demo button: the worst case is a few extra test notifications to the user's *own* devices (the endpoint never sends to anyone else). If you need a strict limit across processes, store the last send time in a shared place, for example a `push_test_log` row in Supabase or Redis, and check it before sending. Keep the production backend on a **single worker** until then (`--workers 1`).

- **No effect on the real job:** nothing is written back. `last_severity` and `last_notified_at` stay as they were, so a real warning is still sent when it starts.
- **Result:** `status` is `sent`, `failed`, `disabled` (push not configured) or `no_subscription`, with `sent` / `total` counts. The UI shows it under the button.

Needs `SUPABASE_URL` and `SUPABASE_ANON_KEY` on the backend (503 otherwise) plus the VAPID keys. Tests: `tests/test_demo_push.py`.

### Web Push: how it works

1. A signed-in user picks a location on `/alerts` and taps **Alert me**.
2. The browser subscribes with the server's VAPID public key (from `GET /api/push/config`).
3. The subscription is stored in `public.alert_subscriptions` (Supabase migration 7, RLS: own rows only).
4. On a schedule, the job does the following:
   - reads all subscriptions with the service-role key
   - fetches weather once per ~1 km cell
   - runs the alert engine
   - sends a push only when the level changes to `warning` from anything lower
5. **Repeats:** while the level stays `warning`, nothing more is sent. The job re-arms when the level drops.
6. **Delivery outcomes:**
   - Failed and disabled sends keep the previous level, so the next run retries.
   - Subscriptions the push service reports as gone (404/410) are deleted.

## Setup

### 1. Database

In the Supabase SQL editor, run `supabase/migrations_6_7.sql` on a database that already has sections 1–5 of the schema. On a new database, run `supabase/schema.sql` instead. Both are idempotent; migrations 6 and 7 add `profiles.role` and `alert_subscriptions`. The last statement of `migrations_6_7.sql` prints a check: `profiles.role` defaults to `'citizen'`, and `alert_subscriptions` has RLS on with 2 policies.

### 2. VAPID keys

VAPID keys identify your server to the browsers' push services. Generate one pair per deployment and keep it: if the keys change, every existing subscription stops working and users have to tap **Alert me** again.

**Option A: Python (no extra install).** `cryptography` comes with `pywebpush`. From `backend/` with the venv active:

```bash
python -c "import base64; from cryptography.hazmat.primitives.asymmetric import ec; from cryptography.hazmat.primitives import serialization as s; k = ec.generate_private_key(ec.SECP256R1()); b = lambda x: base64.urlsafe_b64encode(x).rstrip(b'=').decode(); print('VAPID_PUBLIC_KEY=' + b(k.public_key().public_bytes(s.Encoding.X962, s.PublicFormat.UncompressedPoint))); print('VAPID_PRIVATE_KEY=' + b(k.private_numbers().private_value.to_bytes(32, 'big')))"
```

It prints two lines, ready to paste into `backend/.env`:
- `VAPID_PUBLIC_KEY`: the 65-byte uncompressed P-256 public key, base64url (87 characters, starts with `B`). Browsers use it as the `applicationServerKey`.
- `VAPID_PRIVATE_KEY`: the 32-byte private key, base64url (43 characters).

**Option B: Node.** This gives the same format:

```bash
npx web-push generate-vapid-keys   # one-off CLI run; not added to package.json
```

**Check it.** Restart the backend, then call `GET /api/push/config`. It should return `"available": true` and your public key. The private key is never returned.

Never commit the private key, and never put it in a `NEXT_PUBLIC_*` variable. The frontend gets the public key from `/api/push/config`.

### 3. Backend environment (`backend/.env` or the host's secrets)

| Variable | Purpose |
|----------|---------|
| `VAPID_PUBLIC_KEY` | Base64url public key (served to browsers by `/api/push/config`) |
| `VAPID_PRIVATE_KEY` | Base64url private key. **Backend only** |
| `VAPID_SUBJECT` | `mailto:` or `https:` contact for push services |
| `SUPABASE_URL` | Already used by the backend |
| `SUPABASE_SERVICE_ROLE_KEY` | Lets the job read every subscription (bypasses RLS). **Backend only; never expose it to the frontend** |
| `ALERT_JOB_TOKEN` | A long random string that guards `POST /api/alerts/check` |

### 4. Install the sender

`pywebpush==2.5.0` is pinned in `backend/requirements.txt`, so `pip install -r requirements.txt` installs it. If it is missing or the VAPID keys are not set, `/api/push/config` reports `available: false` with a reason. Users can still subscribe, but the job counts sends as `disabled` and does not mark anyone as notified.

Each send has a 10 s timeout. A network error or a push-service error other than 404/410 counts as `failed`, and the next run retries it.

### 5. Schedule the job

Run it every 10–15 minutes, either directly:

```bash
cd backend && python -m dissemination.job
```

or over HTTP:

```bash
curl -X POST -H "X-Job-Token: $ALERT_JOB_TOKEN" https://<api-host>/api/alerts/check
```

Both print or return a report with `checked`, `became_high`, `sent`, `gone`, `failed`, `disabled` and `weather_errors`.

**The job must run with the backend venv active** (or with `backend\.venv\Scripts\python.exe` directly). The system Python does not have `pywebpush`, `httpx` or `python-dotenv`, and the job would either fail to import or report `push_available: false`.

#### Windows (PowerShell)

```powershell
# 1. Activate the venv (from the repo root)
cd backend
.\.venv\Scripts\Activate.ps1
# If scripts are blocked: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

# 2. Run the job once (reads backend\.env)
python -m dissemination.job

# Without activating, the same thing:
.\.venv\Scripts\python.exe -m dissemination.job
```

Call the HTTP trigger with `Invoke-RestMethod`. Read the token from your environment rather than typing it into the command history:

```powershell
$env:ALERT_JOB_TOKEN = "<paste your token>"   # current session only
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8000/api/alerts/check" `
  -Headers @{ "X-Job-Token" = $env:ALERT_JOB_TOKEN } |
  ConvertTo-Json -Depth 5
```

Scheduling on Windows (every 15 minutes, Task Scheduler):

```powershell
$py = (Resolve-Path .\.venv\Scripts\python.exe).Path
$action = New-ScheduledTaskAction -Execute $py -Argument "-m dissemination.job" -WorkingDirectory (Get-Location).Path
$trigger = New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 15)
Register-ScheduledTask -TaskName "WeatherGPT alert job" -Action $action -Trigger $trigger
```

**Env var names.** The backend reads `SUPABASE_URL` and `SUPABASE_ANON_KEY`, not the frontend's `NEXT_PUBLIC_` names. If `backend\.env` only has the prefixed names, the backend and the job log a warning telling you to rename them; they are never used as a fallback. Every variable is listed in the root `.env.example`.

## Thresholds: one source of truth

Every hazard rule is in **`backend/thresholds.py`**: hazard, level, comparator, value, unit and window. Everything reads it:

| Surface | How it uses the rules |
|---------|-----------------------|
| Alert engine (`alerts/engine.py`) | Thresholds **and** levels for `/api/alerts` |
| Dashboard and map status | `/api/alerts` (the alert banner is the only location status; the old chat-driven "Weather Intelligence" card is gone) |
| District risk board (`roles/risk.py`) | `evaluate_alerts` |
| Web Push job (`dissemination/job.py`) | `evaluate_alerts` |
| CAP export | Each alert's `threshold_value` |
| Chat advisories (`advisory.py`) | Same values. Severity comes from the rule level through `ADVISORY_SEVERITY`: warning is high; watch and advisory are moderate. |
| `/alerts` threshold table | `GET /api/alerts/thresholds` (never hard-coded in the UI) |

| Rule | Level | Threshold | Window |
|------|-------|-----------|--------|
| Heavy rain | watch | ≥ 15 mm | 24 h total |
| Extreme rain | warning | ≥ 50 mm | 24 h total |
| High heat | advisory | ≥ 35 °C | 24 h maximum |
| Extreme heat | warning | ≥ 40 °C | 24 h maximum |
| Cold | advisory | ≤ 5 °C | 24 h minimum |
| Strong wind | watch | ≥ 40 km/h | 24 h maximum |
| Gale | warning | ≥ 65 km/h | 24 h maximum |
| Thunderstorm | watch | WMO 95 | current |
| Thunderstorm with hail | warning | WMO 96, 99 | current |

These are WeatherGPT's conservative fallbacks, not IMD criteria.

**Alerts vs chat advisories:**
- An alert covers the location's current conditions plus the next 24 h.
- A chat advisory covers the period the question asked about, and its panel is labelled with that period (for example "Advisory · Mon 2 Nov, 00:00–23:00").

**When changing a rule:**
- Edit `thresholds.py` and run `tests/test_thresholds.py`.
- Regenerate the Playwright fixture `weathergpt-web/e2e/support/thresholds.json`; the test prints the command.

## CAP mapping

| WeatherGPT | CAP `severity` | `urgency` | `responseType` |
|------------|----------------|-----------|----------------|
| warning | Severe | Immediate | Prepare |
| watch | Moderate | Expected | Monitor |
| advisory | Minor | Future | Monitor |

Every info block also carries:
- `category` Met and `certainty` Likely (these are forecast thresholds, not observations)
- `expires` 12 h after the alert
- an area `<circle>` of 10 km around the point
- `parameter`s with the triggering value and threshold

Tests: `tests/test_dissemination.py`.
